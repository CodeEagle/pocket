# Visual novel render backend audit

This read-only audit checks the pinned macOS renderer, the proposed `FragmentShader` LOD path, and the smallest evidenced native-renderer reuse point. It does not change the current renderer or claim a performance gain.

## Current macOS surface already uses 4x MSAA

The repository pins Flutter 3.47.9 in `.fvmrc`. `demo/macos/Runner/Info.plist` does not override `FLTEnableImpeller`. In the pinned engine, `FlutterDartProject.enableImpeller` defaults to `YES` when that key is absent, and `FlutterEngine.runWithEntrypoint` adds `--enable-impeller=true` unless explicitly disabled (`.fvm/flutter_sdk/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterDartProject.mm:77-84`, `FlutterEngine.mm:672-685`). The current Demo therefore uses Impeller on Metal by default.

The macOS swapchain target uses a four-sample attachment: `SwapchainTransientsMTL::GetMSAATexture` creates `SampleCount::kCount4` (`.fvm/flutter_sdk/engine/src/flutter/impeller/renderer/backend/metal/swapchain_transients_mtl.mm:50-68`), and `SurfaceMTL::WrapTextureWithRenderTarget` binds it as the color attachment with multisample resolve (`surface_mtl.mm:82-87`). Metal capabilities advertise offscreen MSAA (`context_mtl.mm:71-81`). `OptionsFromPass` copies `pass.GetSampleCount()` into pipeline options (`entity/contents/contents.cc:19-31`); `VerticesSimpleBlendContents::Render` and `VerticesContents::Render` use those pass-derived options for their draw-vertices pipelines (`entity/contents/vertices_contents.cc:154-159, 189-199`).

`drawVertices` does not consume `Paint.isAntiAlias`: its display-list flags omit the anti-alias attribute (`display_list/dl_op_flags.h:369-376`). That flag omission does not mean the current Impeller/Metal window has no edge coverage: the pass and mesh pipeline are four-sample. `Picture.toImage` on this backend also goes through Impeller's snapshot path; `DisplayListToTexture` selects an MSAA offscreen target when supported (`lib/ui/painting/picture.cc:78-104, 263-275`, `shell/common/snapshot_controller_impeller.cc:64-68`, `impeller/display_list/dl_dispatcher.cc:1244-1272`). Flutter tests run through a different backend may not represent this macOS app path.

This closes the open question about missing edge AA on the current window. It does not settle texture minification quality or vertex transport cost.

## Demo Retina pixel chain and live window

The normal Demo entry point calls `PocketSystemHostApplication.fromBundledAssets` from `demo/lib/main.dart:69-86`. The host mounts `PocketGuestSession` for both its root and child application surfaces without supplying a fixed `viewport` (`sdk/lib/src/pocket_system_host.dart:914-955`); `PocketGuestSession` creates `PocketView` and passes through that null viewport (`sdk/lib/src/pocket_app.dart:184-214`). `PocketView` opens its normal FFI runtime at the logical host constraints and supplies `pocketRasterDensity(View.devicePixelRatio)` (`sdk/packages/pocket_flutter/lib/src/pocket_view.dart:1499-1531`); that raster density is `ceil(DPR)` clamped to 1–4 (`sdk/packages/pocket_flutter/lib/src/pocket_display.dart:1-6`). Its normal self-owned runtime path uses the exact Pocket frame size instead of preview contain fitting (`sdk/packages/pocket_flutter/lib/src/pocket_view.dart:6298-6335`).

The macOS runner installs a standard `FlutterViewController` in its `NSWindow` (`demo/macos/Runner/MainFlutterWindow.swift:4-13`). The pinned `FlutterView` asks AppKit to inherit its contents scale from the window and sends a reshape when backing properties change (`FlutterView.mm:142-151`); the engine reports `convertRectToBacking(view.bounds)` and `view.layer.contentsScale` as Flutter window metrics (`FlutterEngine.mm:1193-1213`). The painter keeps coordinates logical, scales only by the surface-to-frame fit, and receives the exact view DPR for pixel snapping/LOD calculations (`sdk/packages/pocket_flutter/lib/src/pocket_view_painter.dart:297-302, 328-334`; `sdk/packages/pocket_flutter/lib/src/pocket_view.dart:6323-6335, 6614-6639`). In the normal host-sized path this surface fit is 1:1; Flutter applies the window's backing scale when rasterizing the scene. The macOS Flutter surface creates an IOSurface/Metal texture at its supplied pixel dimensions (`FlutterSurface.mm:92-136`), and the surface manager presents it at logical dimensions by dividing its size and offset by the containing layer's `contentsScale` (`FlutterSurfaceManager.mm:201-215`). This source path does not introduce a lower-resolution full-window surface before presentation.

Read-only AppKit/CoreGraphics inspection at **2026-11-08T01:59:12Z** found one screen with frame 1920×1080, visible frame 1920×969 at y=81, and `backingScaleFactor = 1.0`. The onscreen `pocket_host` window was PID 15377, window ID 18690, bounds x=560 y=232 size 800×632, alpha 1, layer 0. Thus this live run is on a 1× display; it is not runtime evidence of a Retina/2× window. The read-only query observed the screen and window but did not inspect Flutter's `View.devicePixelRatio` value or the view layer directly; source shows how that value is derived from the window backing scale. No screenshot or Flutter test DPR override was used for this observation.

The native `raster_density` parameter is sampled at runtime creation (`pocket_runtime.dart:630-655, 709-749`; native storage is in `sdk/native/src/lib.rs:500-502, 4324-4405`). A Flutter backing-scale change updates the painter's DPR and marks the scene for rebuild (`pocket_view.dart:1111-1119, 1331-1345`), while the resize call changes only the logical viewport (`pocket_view.dart:1425-1458`). No live raster-density update entry point appears in the current SDK source. Therefore, if a running window moves from a 1× screen to 2× without recreating the guest, Flutter's Canvas should adopt 2× while core-generated bitmap resources can retain their boot density. The inspected run started on 1×; no Retina density transition was observed.

The SDK contains no full-scene `PictureRecorder`/`Picture.toImage` scale-down path. Its only such call is `_downsampleMeshImage`, which creates descending-resolution *source texture* variants for mesh minification when `POCKET_MESH_IMAGE_LEVELS` is enabled (default true; `sdk/packages/pocket_flutter/lib/src/pocket_view.dart:3874-3880, 3902-4007, 4009-4027`); the mesh painter chooses among those images and currently binds the chosen image with `FilterQuality.low` (`sdk/packages/pocket_flutter/lib/src/pocket_view_painter.dart:598-611, 622-641`). `saveLayer` is used for mesh blend/mask op bounds (`pocket_view_painter.dart:341-362`). These are bounded texture/layer intermediates, not an explicit low-resolution full-window raster stretched to the window. Source inspection cannot rule out runtime compositor caching; confirming actual render-target sizes would require a GPU/runtime capture, which was not performed.

## Pocket PAK raw images reach Impeller's mip generator

For native frame resources, `PocketView._loadImageResource` defaults to `PocketPakImages.decodeResource` (`pocket_view.dart:4077-4102`). That function converts and premultiplies the PAK pixels, then `_decodePremultipliedRgba` calls `ui.ImageDescriptor.raw(... rgba8888)`, `instantiateCodec()`, and `getNextFrame()` (`pocket_assets.dart:47-69, 82-87`). Flutter's raw descriptor creates an uncompressed `ImageDescriptor`, and its single-frame codec sends `getNextFrame()` through the isolate's configured `ImageDecoder` (`image_descriptor.cc:154-176, 194-208`; `single_frame_codec.cc:32-82`). With this Demo's Impeller backend, `ImageDecoder::Make` selects `ImageDecoderImpeller` (`image_decoder.cc:15-30`), whose `Decode` uploads through `UploadTextureToPrivate` (`image_decoder_impeller.cc:669-738`). That upload allocates `size.MipCount()` levels and explicitly calls `GenerateMipmap` (`image_decoder_impeller.cc:452-504`; a Metal resize result likewise regenerates its full chain at `508-530`).

So the decoded `ui.Image` has a complete mip chain on this path. The current Pocket texture-triangle painter sets `FilterQuality.low`, however, which maps to linear sampling with the base mip only (`image_filter.cc:29-45`; `skia_conversions.cc:24-45`); its separate image variants above remain the mip-selection path for those meshes. The full decoded-image chain is available to Impeller consumers that request mip-linear sampling, but it does not silently replace that painter's explicit selection.

## FragmentShader cannot see the mesh UVs

Pocket's current mesh path supplies UVs in `ui.Vertices.textureCoordinates` and samples a selected LOD image with an `ImageShader` (`sdk/packages/pocket_flutter/lib/src/pocket_view_painter.dart:627-751`). A custom `FragmentShader` can bind image samplers and can use derivatives available in the Impeller shader language, but the Flutter runtime-effect vertex interface does not pass mesh UVs to it:

- The pinned `runtime_effect.vert` accepts only `position` and writes that value to `_fragCoord` (`.fvm/flutter_sdk/engine/src/flutter/impeller/entity/shaders/runtime_effect.vert:12-20`). The Impeller runtime-effect include returns `_fragCoord` from `FlutterFragCoord()` (`impeller/compiler/shader_lib/flutter/runtime_effect.glsl:8-22`).
- Flutter's mesh geometry conversion carries both position and `texture_coords` for the built-in textured-vertices pipeline (`impeller/display_list/dl_vertices_geometry.cc:147-205`). Runtime effects instead use the generic `GetPositionBuffer` callback (`impeller/entity/contents/color_source_contents.h:239-246`); they receive position local coordinates, not that separate interpolated UV attribute.
- The shader derivatives `dFdx` and `dFdy` are used by pinned Impeller shaders (`impeller/entity/shaders/circle.frag:62-66`, `uber_sdf.frag:143-147`). The pinned engine compiles runtime-stage GLSL for Metal (`impeller/compiler/compiler.cc:477-497`). I did not find a pinned `FragmentProgram` regression that exercises derivatives or a custom varying, so the source supports derivative availability on Impeller but does not verify a custom runtime effect for this use.

Consequently, the suggested shader cannot compute per-fragment LOD from the mesh's UV gradients using the existing `Canvas.drawVertices` + `FragmentShader` API. It cannot replace the current CPU triangle-density estimate with local UV derivatives without an engine interface that exposes the UV varying. Four image samplers alone do not fill this gap; the engine's `RuntimeStage::Create` also documents that its image-binding bookkeeping is only guaranteed for a single `sampler2D` (`impeller/runtime_stage/runtime_stage.cc:81-85`). Keep this as an unverified engine-extension idea rather than an available SDK-only optimization.

## Smallest native-renderer reuse point

The retained parent `/Volumes/ORICO/Development/Github/pocketjs_flutter_demo` was searched with `pocket_host/` excluded. It contains no reusable native texture producer implementation outside that directory. Its audit reports mention `PocketHardwareManager.swift` and `CameraHardware.kt` only as excluded `pocket_host` implementations (`POCKET_SDK_AUDIT_REPORT.md:207, 222, 283`); those reports are not implementation source.

The current SDK already has the Flutter-side consumer and trusted handle lifecycle: `PocketViewController.authorizePlatformTexture`/`revokePlatformTexture` (`sdk/packages/pocket_flutter/lib/src/pocket_view.dart:65-79`), `PocketView` renders an authorized ID as Flutter `Texture` for a JS-owned `platformTexture` surface (`pocket_view.dart:6733-6767`), and `HardwarePlugin.forPocketViewController` wires capability registration to that authorization (`sdk/packages/pocket_hardware/lib/src/hardware_plugin.dart:8-14`). Reuse this consumer path; it does not provide Live2D frames.

The official Cubism Native 5-r5 tree contains `CubismRenderer_Metal::StartFrame(commandBuffer, renderPassDescriptor)` (`sdk/packages/pocket_live2d/.cache/cubism-sdk-native-5-r5/CubismSdkForNative-5-r.5/Framework/src/Rendering/Metal/CubismRenderer_Metal.hpp:141-150`), and its implementation creates the encoder from the supplied descriptor (`.../CubismRenderer_Metal.mm:580-596`). The current Pocket Live2D macOS podspec compiles only `Classes/**/*` and links the Cubism Core xcframework (`sdk/packages/pocket_live2d/macos/pocket_live2d.podspec:10-17`); it does not include the official Framework Metal renderer or register a Flutter texture. The current FFI exposes drawable arrays (`sdk/packages/pocket_live2d/native/include/pocket_live2d_core.h:53-71, 115-121`), which Dart copies into serialized drawables, while JS evaluates motion, expression, physics, pose and parameter values before mapping those drawables to Novel meshes (`sdk/packages/pocket_vn/src/live2d.ts:91-160`).

For a future transport-performance experiment, the minimal architectural gap is a macOS native producer that accepts the per-frame model parameters already computed by JS, invokes the official Metal renderer, and exposes its resolved output through Flutter's external-texture registration. The existing JS `platformTexture` surface can then compose that texture without adding a Flutter-side model state machine. The public macOS texture contract is `FlutterTexture.copyPixelBuffer` plus `FlutterTextureRegistry.registerTexture` (`.fvm/flutter_sdk/engine/src/flutter/shell/platform/darwin/common/framework/Headers/FlutterTexture.h:21-64`). This producer bridge and the required image lifetime/frame notification have not been implemented or validated here. The current four-sample surface means this is a transport/performance candidate, not a repair for missing window-edge AA.
