# WeChat Mini Program host

## Scope and acceptance status

This is an SDK target adapter for a generated WeChat consumer project. It embeds the pinned PocketJS Runtime WASM and a real QuickJS 0.12.2 QJBC guest. It does not interpret an arbitrary WeChat package, and it does not render a second WXML layout tree.

The target mounts one Guest on one primary surface. It does not implement `PocketSystem` app catalogs or dynamic child compositing; the builder rejects a project root containing `pocket.system.json` instead of creating fake `ui.__surfaces` state. It also has no Worker/HTTP/`io.offload` wiring: a `pocket.json` containing `domains.worker` is rejected before Guest compilation, native bytecode/Cargo work, or output creation. The retained standalone `demo/js/apps/lobby` guest is the reference consumer for the local pointer acceptance gate.

The target is implemented under `sdk/targets/wechat/` and built by `sdk/scripts/build_wechat.ts`. The SDK still has its two existing entry points; a generated consumer project is written to the caller's output directory and is not added as another repository demo.

The local acceptance gate is `sdk/targets/wechat/tests/qjbc_pointer.mjs`. It instantiates the generated WASM in Node, boots the actual PocketJS Runtime, finds the retained Lobby guest's “Increment lobby counter” action through core inspection/layout, sends logical contact down/up samples at DPR 2, and checks that both the QJBC guest's `count` and `visits` values change from `0` to `1` with a changed next core-rendered pixel buffer. It returns the actual `platform.storage.get` host request through the WASM adapter and asserts that `web_destroy` releases the Guest and Runtime. This is a Node WebAssembly integration test, not WeChat DevTools or physical-device acceptance. WeChat DevTools was not present on this machine; `/Applications/WeChat.app` was left unopened, and no login or publish operation was performed.

## Build and local verification

The build requires Bun, Python 3, Cargo with the `wasm32-unknown-unknown` target, and an LLVM-compatible `llvm-ar`/`emar` (auto-detected from EMSDK or Homebrew; override with `POCKET_WECHAT_LLVM_AR`). Prepare the pinned upstream workspace first. From the repository root, provide a PocketJS consumer directory containing `pocket.json` and `manifest.json`, plus a new or empty output directory:

```sh
python3 sdk/scripts/prepare_upstream.py
rustup +1.98.1 target add wasm32-unknown-unknown
RUSTUP_TOOLCHAIN=1.98.1 bun sdk/scripts/build_wechat.ts --project-root=demo/js/apps/lobby --outdir=/tmp/pocketjs-wechat-consumer
node sdk/targets/wechat/tests/qjbc_pointer.mjs /tmp/pocketjs-wechat-consumer
```

The builder compiles the app through the existing `sdk/scripts/build_guest.ts`, validates and embeds its QuickJS bytecode envelope and PAK, copies the pinned upstream Runtime into a temporary workspace, applies target-only patches there, and writes a consumer scaffold. It fails if the pinned source marker, source patch anchors, bytecode metadata, or support-file hashes do not match. It does not fall back to JavaScript source evaluation.

## Runtime path

1. `buildGuest` emits the consumer's `quickjs-bytecode` entry and PAK. The bytecode envelope is admitted with the same `sdk/native/src/bytecode.rs` validation logic used by the native host.
2. The adapter instantiates the pinned PocketJS Runtime and `RquickjsGuest` with the canonical bindings. `RquickjsGuest::evaluate` is disabled in this target; the guest enters through `JS_ReadObject(..., JS_READ_OBJ_BYTECODE)` and `JS_EvalFunction` only.
3. The ordinary PocketJS `Runtime`, UI, package registry, input encoder, DrawOps, font/glyph table, clips, rasterizer and resource lifecycle produce the retained draw list and pixel output. PAK assets are admitted by the same Runtime asset registry; the target does not recreate layout in WXML.
4. `web_pixels` supplies the Runtime's software-rendered RGBA frame to a WeChat `Canvas2D` `putImageData` call. Image and compositor resources continue through Runtime surfaces and the core compositor.
5. Canvas touch events become `Contact` records. The Runtime resolves hit bounds at contact-down, packs the existing guest frame input, and calls the QJBC guest. Device-pixel ratio is applied to canvas allocation; guest coordinates remain logical pixels.

The QJBC probe established two separate gates. The isolated 213-byte PJBC fixture at `/private/tmp/quickjs_wasm_guest.qjbc` (SHA-256 `3bef3ef2f8c23ffa0592bd4926f4baffc6f0216614c55ca2668f21f08da70891`; source `/private/tmp/quickjs_wasm_guest.js`, SHA-256 `257f5f1303557c2018f3ceaeac16a851e55357a78bb2ce26ba608b3e5da65dde`) contains 89 bytes of QuickJS payload; `probe_qjbc` executed `frame(41); result` and returned `42` under rquickjs 0.12.2 WASM (probe module SHA-256 `35e2184c64c2e884e3c9ea34d0400beea2d3bbf4328f9dfc2cc02d81fec982af`). That probe imports a debug `host_assert` hook, so it records QuickJS bytecode execution only; it is not the PocketJS Runtime target package or a WeChat host pass. The reference Lobby consumer is separately checked by the pointer/next-frame test above.

The first real Lobby QJBC boot exposed a 32-bit stack-limit underflow, not a bytecode ABI mismatch: QuickJS 0.12.2 computes `stack_limit = stack_top - stack_size` with `uintptr_t`, while the upstream 4 MiB ceiling exceeded the default 1 MiB WebAssembly linker stack. The subtraction wrapped and `JS_ReadObject` returned “Maximum call stack size exceeded.” The target now explicitly links a 1 MiB WASM stack and caps QuickJS at 512 KiB, leaving headroom below `stack_top`; the same real Lobby QJBC then loaded and handled touch input. The builder applies this patch only in its temporary WeChat workspace. The target `getLayout` callback passes the current `Ctx` as a callback argument instead of capturing it, so host disposal does not create a Runtime/Context reference cycle.

Final local evidence from the generated package: QJBC `161,360` bytes (payload SHA-256 `3c377dd377ca7b948e98aeb528ee30d860ea0ccad2c2b84591b146bff9393949`; QuickJS ABI `5ab2246bcbd64b9d66e396043be05c2f77e7a6ab78e3125c56f8a1f62019a021`), PAK `259,632` bytes, WASM `2,647,634` bytes (SHA-256 `fdc1e31b98fbafe5bf7c1f6e68d43e5e380eab7c4c121f4b948af5456c22dd79`), Brotli WASM `774,428` bytes (SHA-256 `053bc334be04e57148b3b6022bc02c20e3882ee54ddd0996dc79ea2ef0c2f94e`). The checked test result was `Lobby counter 0 -> 1 after contact down/up and next frame`; it also verified both `count` and `visits`, a changed core RGBA frame, delivery of the Lobby `platform.storage.get` response, and `web_destroy`. The WeChat `pocket.getLayout` callback adds parent-local core positions to return screen-relative flex geometry without paint transforms; the test independently walks the complete parent chain because `layout_of` returns node-local rectangles and a parent may be allocated after its child. These hashes and Node results do not claim WeChat DevTools or device validation.

## WeChat host behavior

- **Frames:** the host queries PocketJS work state after a frame. Continuous guest work uses Canvas `requestAnimationFrame` when available, with a timer fallback. Idle work schedules only the next timer deadline and skips idle simulation frames in the existing PocketJS scheduler. Input, host responses, resize and visibility changes wake the guest. The host does not call `setData` with a rendered tree each frame.
- **Canvas and resources:** the host uploads the RGBA output to Canvas2D. Layout, glyphs, clipping, textures, and disposal remain in PocketJS core and PAK. WXML contains only the canvas, an optional native input, and an error message.
- **Pointer:** `touchstart`, `touchmove`, `touchend`, and `touchcancel` are represented as contact samples. Cancelled contacts are marked for the existing input encoder. Touches are cleared and cancelled on page hide.
- **IME:** PocketJS text input surfaces are represented by a native Mini Program `<input>`. Input, confirm and blur return through `__pocketTextInputEvent`. Keyboard-height changes resize the logical view and wake rendering.
- **Host requests:** `host.request` packets are queued and drained outside the Rust/WASM callback. The queue and in-flight request count are each bounded at 32; requests time out after 15 seconds. A manifest must declare the requested capability. A configured permission handler can approve or cancel custom requests; custom handlers receive an abort signal. Page hide and disposal abort pending requests and return cancellation responses.
- **Storage:** the built-in adapter serves `platform.storage.get`, `.set`, `.remove`, and `.keys` when the matching method capability (or aggregate `platform.storage`) is declared. Keys are namespaced by app id and namespace. Values are JSON and capped at 1 MiB per key; WeChat's aggregate storage quota still applies. Other capabilities require `registerCapability` and are rejected as `unconfigured` when no handler exists.
- **Lifecycle:** page hide cancels scheduled frames, outstanding host requests and IME focus. Page unload removes window/keyboard listeners, cancels request timers, destroys the PocketJS Runtime and releases the WASM host.

Synchronous custom provider operations are not emulated by asynchronous WeChat APIs: the target reports `UnsupportedOperation` for those provider calls. No BLE, arbitrary VFS, or filesystem I/O implementation is advertised. Applications can implement asynchronous capabilities with `registerCapability`; PAK assets are handled by the ordinary PocketJS package registry.

## Previous demo and ablation

The pre-existing `/Volumes/ORICO/Development/Github/pocketjs_flutter_demo/wechat_host/` was inspected with its `pocket_host/` subtree excluded; the audit covered the page, recursive `components/pocket-node/` and `core/wx_pocket_host.js`. Its page implements a button-driven count and modal-open state. The modal is rendered by the recursive WXML component; that page does not show a native text input. `core/wx_pocket_host.js` keeps nodes in a JavaScript `Map`; every insert, text change or focus change calls `syncToWeChatDataTree()`, which sends the entire root object through `page.setData`. The same file has a small in-memory store backed by synchronous WeChat storage, plus BLE and VFS helpers whose implementations are not sufficient to claim those services.

That host did not instantiate PocketJS Runtime or a PocketJS Guest. Its `flushDrawListToWxCanvas` handled only `fillRect` and `arc`. `WxPocketSharedStore` was a small cache backed by synchronous WeChat storage; the BLE manager marked itself connected before/around one connection request and delivered manually pushed packets; `resolveVfsPath` only constructed a path. These pieces are not treated as proof of runtime, rendering, storage, BLE or VFS parity.

The target keeps interaction state and hit testing in the PocketJS Guest: core layout determines hit bounds, touch frames reach the same Guest, and the next DrawOps frame is rendered by the core. It provides a native input overlay for Guest text-input events and a declared asynchronous storage capability. A modal must be part of the Guest's DrawOps on its primary surface; the old recursive WXML node/modal tree is not reproduced. The redundant second node/layout tree, repeated full-tree `setData`, and reduced `fillRect`/`arc` renderer were removed from the target. The Lobby consumer's counter and storage request work through its real Guest; its cross-app message and return-result calls need a multi-app host and return `unconfigured` on this single-Guest target. The current Showcase root is a multi-app `PocketSystem` SystemUI and cannot boot on this single-surface target. A diagnostic build using its real 317,048-byte QJBC and 334,192-byte PAK reached guest execution and reported `PocketSystemError: ui.__surfaces must match every installed child in the System catalog`; the builder now rejects that SystemUI project shape before build. The standalone Lobby app validates a real Guest without claiming dynamic child compositor support. The pointer test also returns a host response for the Lobby's real `platform.storage.get` request to exercise the Guest response path; this Node-side packet does not exercise WeChat's `wx` storage API.

## QuickJS WASM build choice and provenance

The formal target is pinned rquickjs/QuickJS 0.12.2 QJBC, compiled for `wasm32-unknown-unknown`. The app's QuickJS source is compiled during guest build; the generated consumer embeds only the admitted QJBC and PAK. No JavaScript source evaluator fallback is provided.

The pinned 0.12.2 `rquickjs-sys` crate does not natively expose the needed `wasm32-unknown-unknown` target. The target build overlays the official rquickjs 0.14.0 WebAssembly shim and wasi-libc support files while leaving the actual QuickJS 0.12.2 sources and C ABI unchanged. `sdk/scripts/build_wechat.ts` fetches the exact `rquickjs-sys 0.14.0` crate archive, checks SHA-256 `cee271d0eeba64f0915b846cb7ae02e16faf3dfdffdca91731101d9d30fe3423`, extracts only the shim, official `wasm32-wasip1` bindings, wasi-libc headers, archive and NOTICE into ignored `sdk/.cache/wechat/rquickjs-sys-0.14.0/support/`, and stores license and provenance there. The WASI include tree is checked at SHA-256 `3c9e8cf31f92df2a82da6e436ab26bae97d0b852e4004d7d3af36beca66aee63`; shim, bindings, archive, NOTICE and license are also checked against fixed hashes. The vendored `libc.a` is a wasi-sdk-24 wasm32-wasi archive; its originating sysroot and license are described in the preserved upstream `NOTICE.md`.

The shim's clock import is `env.__rquickjs_host_now_us` (`f64`, microseconds). It supplies QuickJS time/clock calls and the Rust guest turn deadline without WASI imports. WeChat's portable host clock source is `Date.now()` with a nondecreasing clamp; this avoids backwards clock changes but does not provide a high-resolution monotonic oscillator. The other WASM import is `pocket_wechat.host_emit`, used for bounded JSON event delivery. The generated WASM is checked to import only those two functions.

Header/binding checks are target-local: `sdk/targets/wechat/src/wechat_guest.rs` calls the 0.12.2 `JS_ReadObject` signature with `JS_READ_OBJ_BYTECODE`, tests `JS_VALUE_GET_NORM_TAG`/`JS_TAG_EXCEPTION`, and passes the resulting object to `JS_EvalFunction`. The compiler uses the 0.12.2 QuickJS headers and C sources from the pinned PocketJS workspace. The official 0.14.0 binding input has SHA-256 `c3e5e1b99f3dccb78702bc82b2316896fc47b9973f23c4810d6949dafe42a0f5`; the target applies `sdk/targets/wechat/wasm32-unknown-unknown-qjs-0.12.2.patch` (SHA-256 `cb8c7613b08821ad8e5f1d15e5ad3db6d718873c8e26d6ab93538bbbe7ae725e`) and verifies the result hash `ea0b38213d704c274012a42c3303dc93030ba0ad717ec9933e34b8e4d00e3f70`. This compatibility patch adds the opaque 0.12.2 `JSClass`/`JSObject` declarations and `js_realloc2`, restores the 0.12.2 ArrayBuffer free-callback signatures, and removes 0.14-only promise declarations. The integration gates exercise the resulting interface from a genuine QJBC envelope.
