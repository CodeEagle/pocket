# Visual novel Word export

## Source-first review

The retained parent project was inspected outside its `pocket_host/` directory. Its [README](/Volumes/ORICO/Development/Github/pocketjs_flutter_demo/README.md), [Flutter entry point](/Volumes/ORICO/Development/Github/pocketjs_flutter_demo/lib/main.dart), [origin and QA archive](/Volumes/ORICO/Development/Github/pocketjs_flutter_demo/docs/01_ORIGIN_PROPOSAL_AND_QA_ARCHIVE.md), and [dual-host component spec](/Volumes/ORICO/Development/Github/pocketjs_flutter_demo/docs/03_DUAL_HOST_UI_COMPONENTS_SPEC.md) describe a PocketJS Flutter/WeChat showcase and JS-driven rendering. The retained source has no visual novel story model or Word/DOCX export to adapt. Its relevant behavior is keeping application behavior in JS while the Flutter host renders UI; the Editor Word writer follows that split by running only at the Editor's Node/Bun boundary.

The existing reusable story behavior is in `sdk/packages/pocket_vn/src/authoring.ts`: `formatStoryText` serializes all labels and instructions, and `parseStoryText` reconstructs the canonical `StoryDefinition`, including custom JSON fields and unknown instruction data. Existing interchange has an 8 MiB authoring-source cap and guards label/instruction counts in `sdk/packages/pocket_vn/src/interchange.ts`. The ZIP implementation in `sdk/scripts/package_update.ts` already emits deterministic ZIP32 archives. This export reuses those boundaries, adds XML 1.0 scalar validation and a DOCX-part/output cap, and does not add a ZIP dependency or a second serialization model. The Editor's on-disk `story.json` route keeps its existing separate 2 MiB request limit in `sdk/editor/novel.ts`.

## API and contents

`createNovelWordDocument(story: StoryDefinition): Uint8Array` is exported from `sdk/editor/novel-word.ts`. It is synchronous, read-only, requires no asset registry or resolved media, and returns a real ZIP-based WordprocessingML package. It starts with a Title-styled heading and metadata subtitle, then prints every script label as a Heading 1 paragraph (including labels with zero instructions) and every instruction in source order. Each instruction has a `script["label"][index]` source location, its type, and its ID when present.

This is a complete script review document, not a lossless exchange format for every story-level setting. The visible story header includes title, ID, version, and start label; fields such as variable definitions and inventory are outside the script review body.

Dialogue keeps the speaker and full body together; source newlines and tabs become Word line-break and tab elements, and other authoring fields remain visible as additional parameters. Choice prompt, each option and target label are printed explicitly. Other instructions get a human-readable summary and the complete instruction JSON. Unrecognized types are labeled as unknown data, with a note that export does not imply engine support. No asset paths are resolved or embedded.

The package contains only `[Content_Types].xml`, the package relationship, `word/document.xml`, its internal styles relationship, and `word/styles.xml`. It has no external relationships, macros, core/custom properties, timestamps, usernames, or local paths. It uses A4 page dimensions, readable body/parameter styles, and `keepNext` for Heading 1. XML-illegal control characters and unpaired UTF-16 surrogates cause an explicit error; text is escaped, never silently dropped. The authoring source is capped at 8 MiB, each XML part and the final archive at 32 MiB.

The Editor endpoint is `POST /api/projects/:id/novel/export?format=docx`; its body is the current draft's StoryDefinition JSON. The route reuses the bounded streaming reader, enforces the 8 MiB cap even without `Content-Length`, and cancels an oversized request as soon as the byte limit is crossed. It decodes UTF-8 in fatal mode. Export reads the submitted draft and returns attachment bytes without writing `story.json` or Editor history. The existing GET export continues to return the saved JSON story.

## Validation

`sdk/editor/test/novel_word.test.ts` opens the returned bytes with the existing `extractZipArchive`, checks package entries and internal relationship targets, validates styles, A4 geometry, paragraph structure, source locations, every current instruction type plus an unknown future type, choice targets, empty labels, XML escaping, multiline/tab handling, read-only input state, deterministic bytes, invalid XML scalar rejection, and output-size rejection. `sdk/editor/test/novel_word_route.test.ts` covers current-draft POST, unchanged saved story, legacy GET JSON export, strict UTF-8 rejection, request bounds, and early cancellation of an oversized chunked body.

Pinned Bun verification passed with exit 0: `npm exec --yes --package=bun@1.4.4 -- bun test --max-concurrency=1 editor/test/novel_word.test.ts editor/test/novel_word_route.test.ts editor/test/novel.test.ts editor/test/novel_history.test.ts` (28 passed, 0 failed, 82 expectations). The existing real-Guest browser scenario `editor/test/novel_interchange_browser.test.ts` also passed under Bun 1.4.4 (1 passed, 0 failed, 6.27 seconds); it builds and runs the saved story through the pinned Guest pipeline.

The exported `lantern-script.docx` was converted with isolated LibreOffice 26.2.7.3 (AArch64) using a 45-second timeout and a private profile, then read page by page with PDFKit. The PDF has 113 non-empty A4 pages (595.3 × 841.9 points). The source `demo/js/apps/lantern/story.json` at SHA-256 `3df036a67ba2d1f0a9e40ef18a87e14905c8ddc9af9992e993641c3a227143ef` has 117 labels and 531 instructions: all 531 location/type/ID markers appeared in source order; all 255 say bodies, 79 choice options and targets, and 276 non-dialogue JSON blocks were present. Body comparison normalized Unicode whitespace to account for PDF line wrapping; it verifies text coverage, not byte-exact line breaks. All pages had extractable text; 63 pages contained multiple say instructions and one page contained up to nine, so the layout does not force a page break per line. Every non-empty label's first instruction remained with its heading. A one-page unsaved-draft document also retained its empty label, all three instructions, punctuation, quotes, and multiline Chinese dialogue.

Six contact sheets for pages 1–113 and one unsaved-draft contact sheet are under the ignored QA directory `sdk/.pocket-build/novel-word-export-20261108/contacts/` and `unsaved-contacts/`; the manifest is `contacts/contact-sheets.json`. `lo-pages/` and `lo-unsaved-pages/` hold the failed first-pass raster and are marked `DO_NOT_REVIEW_RASTER.md`; use `lo-pages-rerun/` and `lo-unsaved-pages-rerun/` for the corrected PDFKit thumbnails. The LibreOffice reader validated package opening and rendered pagination. Microsoft Word itself was not launched or tested.

Microsoft's WordprocessingML package guidance confirms the relationship-based package and the `document` / `body` / paragraph / run / text structure used here: [Create a package](https://learn.microsoft.com/en-us/office/open-xml/general/how-to-create-a-package), [WordprocessingML document structure](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document), and [paragraph styles](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-create-and-add-a-paragraph-style-to-a-word-processing-document).
