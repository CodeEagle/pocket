# Real save-slot thumbnails

## Source and ownership

This continues [the bounded scene-capture boundary](VISUAL_NOVEL_SCENE_CAPTURE.md). The retained parent sources inspected outside `pocket_host/` are `../pocketjs_flutter_demo/test/pocket_38_components_screenshot_test.dart` (test-only `toImage`/PNG capture), `lib/core/real_hardware_bridge.dart` (camera photo persistence/list/delete), `lib/core/pocketjs_bundle_runner.dart` (camera page filename/path updates), and `ios/Runner/AppDelegate.swift` (native camera capture and photo storage). These preserve real capture and file-lifecycle patterns, but none captures pixels from a running guest. The required adaptation captures the existing child surface through an explicit PocketView capability and persists a bounded PNG; it reuses the existing JS slot manager and renderer, without adding another renderer or Dart save-slot state machine.

The existing pinned `compiler/framework/src/resource.ts` `ResourceImage` binds borrowed texture handles. `@pocket/ui/images` owns their upload/release lifetime through existing `uploadImgEntry`/`freeTexture` APIs. See [dynamic resources](DYNAMIC_IMAGE_RESOURCES.md).

## Contract

Child-only `platform.images.capture/read/list/remove` providers use the trusted child app ID and reject stale session/owner generations around asynchronous work. The fixed mounted `PocketView` capture option comes from negotiated capabilities, rather than temporary foreground availability. Other guests retain the default-disabled capture boundary.

PNGs are immutable SHA-256 objects in app-private `pocket-images/<sha256(appId)>/<id>.png`. No filesystem path is returned to JS. Limits are 256×256 pixels, 512 KiB per PNG, 256 images and 32 MiB per app. A private temporary directory and rename commit the file; metadata is read from PNG headers without a second catalog. Reads verify content identity. Symbolic links are rejected. Reads return the pinned binary IMG format with a power-of-two envelope and transparent padding, not base64 or a numeric JSON array.

Only trusted image-provider sessions admit the required 512 KiB response envelope. Plugin budgeting counts typed binary bytes without JSON expansion, while preserving ordinary JSON limits. The JS component retains dimensions and its owned texture handle after upload, without retaining a second pixel buffer. Layout changes update geometry without rereading the PNG.

## Save references and failure recovery

Canonical save records carry only `thumbnail: {version: 1, id, width, height}`. The existing JS slot manager owns capture, save and cleanup through its existing queue. Raw copy/move/swap preserve the reference; deletion and replacement collect old images only after checking current references. A failed save cleans its new unreferenced capture. Cleanup failures after a successful commit are reported separately. Unknown future thumbnail formats with valid IDs are conservatively retained, while the UI renders only the validated current format.

PNG creation and JSON storage are two commits, not a filesystem-wide atomic transaction. Explicit startup collection handles capture orphans after a crash. The image hook's `list()` must enumerate resources owned by that slot manager: Lantern currently owns the whole image bucket solely for save thumbnails. A consumer sharing its image bucket with other features must filter the hook or implement corresponding ownership before enabling collection. Multiple independent managers/processes writing the same bucket are not covered by the single-manager queue.

Lantern requests at most 192×108 / 20,736 pixels only for explicit saves. Autosaves do not capture or scan all image references. The existing save menu is temporarily hidden and input blocked during capture; progress stays paused. Capture-unavailable/unsupported errors preserve the text save and show a status message. The renderer rejects visible external video/host textures rather than persisting an incomplete scene.
