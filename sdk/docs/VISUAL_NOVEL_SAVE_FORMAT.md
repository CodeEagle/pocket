# Pocket visual novel save format

## Source-first findings

The retained `/Volumes/ORICO/Development/Github/pocketjs_flutter_demo` tree (excluding `pocket_host/`) contains no visual-novel story interpreter or VN save format. Its nearest gameplay example is `mini_apps/app_game_detail/main.js`, which owns a game loop and transient world state; it does not provide narrative rollback checkpoints. The old `View.Keyboard` path recorded in [input reuse notes](INPUT_REUSE.md) is also unrelated to VN persistence. The save model therefore follows the current core interpreter and adapts its serialization boundary; it does not add a Dart state machine or a second runtime.

The core's established V1 model stores the backlog once and keeps bounded rollback checkpoints with `backlogSequence` cursors. A real Lantern route configured for 48 rollback entries and 128 backlog entries exceeded the native storage record limit at 88,006 bytes, so trimming either history would change player-visible behavior. The first compact format removed repeated variables, stage, active dialogue and audio intents across checkpoints. A later expanded-story route still reached 67,130 bytes on V3 because its backlog tuples and rollback-active tuples stored the same rendered dialogue text separately. V4 pools these shared exact strings while retaining the complete history. The current V1 in-memory engine state and UI-facing root save fields stay intact.

## Formats and APIs

`engine.save()` continues to return `pocket-vn-save` version 1. `encodeNovelSaveData(v1)` emits version 4 for persistence. V4 adds one deterministic `state.textPool` of exact rendered strings shared by both history structures. Its backlog entries are `[sequence, lineId, label, index, speaker, portrait, textRef]`, and its rollback `active` pool stores `[label, index, id, speaker, portrait, textRef, revealProgress, autoRemainingMs]`. The remaining rollback state uses the existing first-use pools (`variables`, `stages`, `active`, `audioIntents`) and fixed-width eight-field checkpoint tuples. `visibleText`, `revealedCharacters`, and `complete` are omitted only after the encoder verifies they are derivable and consistent with the referenced complete text; decode recreates those canonical fields. Tuple field names and order are declared in the exported TypeScript types.

V1, V2, and both persisted V3 shapes remain readable. V2 stores rollback active values as ordinary say-state objects and backlog entries as ordinary objects. The first pre-release V3 shape stored object-shaped active values while compacting backlog tuples; the deployed V3 shape stores completed active tuples. The decoder validates either all-object or all-tuple V3 active pools and rejects mixed pools. V4 alone uses text references. Decode expands compact values back to the engine's ordinary V1 save before semantic loading. No backlog or rollback entry is trimmed, and no extra save copy or sidecar is introduced.

Historical NativeSession measurements explain the additional V3 reduction. The earlier V2 full route was 68,734 bytes. V3 with backlog tuples but object-shaped active entries measured 65,526 bytes without the video route; adding the video route measured 70,033 bytes and exceeded the 65,536-byte per-value limit. The active-pool fixture measured 38 unique say states / 21,110 bytes as objects; duplicate `visibleText` strings accounted for 6,382 bytes. The lossless eight-field tuple projection measured 8,458 bytes, a further 12,652-byte reduction including omitted keys and nested locations. These are NativeSession projections for an earlier V3 artifact, not the final V3 active-tuple encoding. The full route ran save/load, rollback, seen-only skip, all three endings and timeout. The associated artifact was Lantern QJBC SHA-256 `cce4f5d6a69cfc37544444f645b2bfd46fbe8a61f2d91667342b0dedeb5dafa8` (816,108 bytes) and PAK SHA-256 `3ead2ebe1661858f7b790e0d9ed932d907ea0246da6bce7e2d673fac8e6ca1a2` (24,793,712 bytes by file stat); runtime ABI was `quickjs-bytecode-v1:5ab2246bcbd64b9d66e396043be05c2f77e7a6ab78e3125c56f8a1f62019a021`. The test checks every route write is V4, each backlog/active text reference resolves, and the text pool contains no duplicate or unreferenced values. The final run log is `/tmp/pocket-lantern-v2-v4-final-route.log`. These are process-local host measurements, not OS-file measurements.

`decodeNovelSaveData(value)` accepts versions 1, 2, 3 and 4 and expands compact saves to the existing V1 shape. V1 passes through without rewriting. `engine.load()` decodes before the core's semantic validation and state transaction; malformed tuples or text references cannot partially replace the live engine. `rebaseNovelSaveDataForLocale()` accepts each version and returns ordinary V1 data after rebasing display text.

The codec validates finite, cycle-free JSON, plain record and array data, exact compact history/pool/tuple shapes, safe indexes and positions, unique pool values, and that every history/text pool entry is referenced. V3 backlog tuples contain exactly seven fields and V3 active tuples exactly eight. V4 uses the same tuple widths, with text references in the final backlog field and active tuple's sixth field; each reference must be in range, and unused or duplicate text-pool entries are rejected. The active tuple must represent a completed say state whose reveal progress equals its rendered text's Unicode code-point count; decoding derives `visibleText`, `revealedCharacters`, and `complete` from that validated text. The encoder rejects noncanonical backlog and active objects instead of silently dropping extension fields. It rejects sparse arrays and noncanonical or out-of-range custom array keys. It does not impose a new fixed JSON nesting ceiling below the existing engine JSON boundary. It copies object fields into prototype-safe records, preserving keys such as `__proto__` as data. Root active state, metadata, save variables, and author story data remain unchanged.

The storage adapter remains the existing one-record-per-slot path in [visual novel slots](VISUAL_NOVEL_SLOTS.md): the host reads one JSON value, the JS boundary decodes and locale-rebases it, and saving encodes to V4 before the same slot write. There is no catalog, second copy, sidecar index, history trim, or larger native quota. Flutter remains responsible only for the storage IO boundary. The existing native binary bridge has a 32-level JSON transport limit in `sdk/native/src/binary_bridge.rs`; the codec's local deep-JSON compatibility does not change or bypass that transport boundary.

## Verification

`save-codec.test.ts` exercises the typed encoder/decoder and live engine load/rollback path. It checks retention of all 48 checkpoints and 49 backlog entries, shared exact-text pooling, V1/V2/both-V3/V4 decode equality, every rollback against V1, completed active tuple reconstruction, malformed text/pool references, tuple/custom-array rejection with atomic load, 140-level JSON round-trip through a rollback pool, finite-number rejection, and prototype-named JSON fields. `localization_save.test.ts` covers compact saves being decoded before locale rebase, including translated backlog, rollback dialogue, timed choice and ending behavior. `demo/js/tests/novel_save_codec_native.test.ts` exercises the pinned QuickJS bytecode guest. Inside the guest it round-trips a 140-level variable through V4 decode, fresh-engine load and rollback, reads both deployed V3 tuple and earlier object-active V3 shapes, and persists a 128-backlog/48-checkpoint V4 record through `platform.storage` before painting the rollback result. Malformed text and pool references leave a live engine unchanged. The 140-level value stays inside QuickJS because the existing native binary bridge limits transported JSON to 32 levels. This fixture uses an injected in-memory host map, not OS-file persistence.

The NativeSession route proofs are `demo/js/tests/novel_native.test.ts` and `demo/js/tests/novel_video_native.test.ts`, run with the pinned Bun 1.4.4 binary from the repository root. They execute the identified Lantern QJBC through the QuickJS host boundary, drive the three-ending/timeout route and the archive/video path, and measure every injected storage value against the 65,536-byte bound. The video test also rebases its actual largest journey save through the English catalog and loads/rolls back the result. NativeSession uses a process-local injected map: it proves the built guest's save encoding and per-value record size, not OS-disk persistence.

Separate earlier real-file evidence is in `demo/integration_test/novel_save_capacity_test.dart`. It observes the app-private `pocket_platform_data.json`, drives the complete route through painted pointer input, fills and verifies all 48 rollback checkpoints, tears down the System host, mounts a new host, resumes the save, and rolls back through pointer input. The older build measured 52,923 bytes on macOS and 53,649 bytes on iOS. These V2-era figures are historical and do not cover the later video route or current active tuple format. They are actual platform file measurements, separate from NativeSession. The current native binary transport's 32-level JSON limit also remains unchanged.
